## 一、项目概述

构建一个部署在飞书群聊中的 AI 办公助手。用户通过自然语言与机器人对话，即可操作飞书文档、多维表格，并响应文档评论中的 @提及。

核心技术路线：DeepSeek 原生 Tool Calls + 飞书 WebSocket 长连接。

## 二、最终架构

飞书群聊 / 文档评论

   FeishuClient (lark.ws.Client + EventDispatcherHandler)

      Mother (Tool Call 循环 + 状态管理)

 (6工具)         (12工具)         (2工具)          (程序调用)

## 四、技术决策与结果

### 决策 1：单机器人 vs 多机器人

**结论：✅ 正确**

飞书平台不允许机器人之间互 @。v1 多机器人架构在飞书上是死胡同。单机器人 + 内部 Skill 是正确的唯一解。

### 决策 2：DeepSeek Tool Calls vs 自定义标记

**结论：✅ 正确**

最初用 `[SKILL_BLOCK]...[/SKILL_BLOCK]` 正则解析 LLM 输出——格式不稳定、参数易错位、多轮调用易中断。改为 DeepSeek 原生 Tool Calls 后，工具调用可靠性显著提升。

代价：每个步骤都是独立 API 调用，复杂任务需要多轮。

### 决策 3：SQL 同步层

**结论：❌ 失败后回滚**

曾尝试让 LLM 只操作本地 SQLite，后台异步同步到飞书。结果多了一层抽象，调试困难，缓存预热不完整，两天后回滚。教训：在 API 本身不稳定的前提下，不要加中间层。

### 决策 4：文档写入策略

**结论：⚠️ 多次反复**

从 Markdown 多类型 Block → 纯文本 block_type=2 → 字段 ID vs 字段名。最终确定：doc_skill 用纯文本 block，bitable_skill 用字段 ID 写记录。格式正确比格式漂亮重要一百倍。

### 决策 5：batch_create vs 分步工具

**结论：⚠️ 倾向分步**

batch_create 把建表+加字段+写数据吞进黑盒，失败时 LLM 无法定位问题。最终拆成 12 个独立工具，LLM 自行编排——每一步失败都能看到明确错误。

## 五、经验教训

### 技术层面

1. **永远不要猜测第三方 API 的请求格式。** bitable_skill 重写了 4 次，花了两整天，因为每次都在猜飞书 API 接受什么参数。如果有官方文档，先读文档再写代码。

2. **单条 API 和批量 API 的请求体格式不同。** `POST /records` 单条用 `{"fields": {...}}`，批量用 `{"records": [...]}`。混用会导致 "field validation failed"。

3. **建表 API 不接受 fields 参数。** `POST /tables` 的 body 中 `{"table":{"name":"x"},"fields":[...]}` 会被飞书静默忽略。字段必须通过独立的 `POST /fields` 逐个添加。

4. **飞书字段创建后需要等待。** `add_field` 返回成功不意味着字段已就绪。写入记录前需要 `await asyncio.sleep(2)` + `list_fields` 验证。

5. **日志是调试的救命稻草。** doc_skill 的写入 bug 花了三天才定位，因为一直没有在 API 调用处加日志。后来在 bitable_skill 加了完整的请求/响应日志，问题立刻清晰。

6. **Mixin 模式的 __init__ 不会被自动调用。** Python MRO 中，Mixin 的 `__init__` 如果不显式调用，会被跳过。用懒初始化（`if not hasattr(self, "_field"): self._field = xxx`）更可靠。

7. **LLM 的上下文限制不是问题。** DeepSeek 有 1M 上下文窗口，100 条长期记忆随便塞。真正限制 LLM 的不是 token 数量，是工具调用的轮次上限（8 轮）。

### 项目层面

8. **先有场景再写代码。** 这个项目最大的问题是"没有真实用户"。所有功能都是自己测自己。如果有一个人在群里真的每天用 Mother 写文档，很多 bug 一小时就能暴露。

9. **分步工具优于一键工具。** 黑盒操作让 LLM 无法调试。给 LLM 细粒度工具，它自己能编排出比我们设计得更好的流程。

10. **工具数量不是越多越好。** 最多时有 25 个 LLM 工具，LLM 选错工具的概率上升。精简到 17 个后稳定性更好。

11. **回滚比硬撑明智。** SQL 层花了两天发现不对，立刻砍掉。如果不砍，后面每个新功能都要兼容两套数据流。

12. **AI 辅助编程的核心不是"让 AI 写代码"，是"让 AI 帮你思考"。** 架构设计、模块拆分、错误分析——这些才是 AI 真正的价值。写代码反而是 AI 最不擅长的（格式错误、API 猜测错误）。

## 六、给后来者的建议

如果你要接着开发这个项目：

1. **先把 bitable 的 add_record 调通。** API 格式已确认——`POST /records` + `{"fields": {"fldXXX": value}}`。需要 `user_access_token` 或以应用身份创建后授权群聊。

2. **升级到 DeepSeek strict 模式。** 文档已研究过——只需换 beta URL + 每个 tool 加 `"strict": true`。能彻底消灭参数格式错误。

3. **优先做 Skill Workshop。** 手动写 Skill 不如让 AI 生成。你已经有代码模板和 AST 安全审计的论证。

4. **别碰 Live2D Python 库。** 用 Web 版 Cubism SDK——官方维护、跨平台、不需要编译。
